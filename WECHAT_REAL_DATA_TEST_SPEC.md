# Shawn Life OS — WeChat Real-Data TDD Test Specification

Status: **Normative pre-implementation test specification**. Production WeChat ingestion code must not be implemented ahead of these contracts.

## 1. Goal

Prove the first real Shawn Life OS DataSource vertical slice using specification-driven, test-driven, and real-data-driven development:

`real WeChat evidence -> acquisition adapter -> shared OCR capability -> WeChat source parser -> versioned source-native schema -> SourceRevision -> deterministic canonical mapper -> immutable canonical history -> query`

AI/LLM inference is **not** required for this slice and must remain disabled for all fact-ingestion acceptance tests.

## 2. TDD rule

For every production implementation task:

1. identify the governing requirement/invariant;
2. select or add a real-data fixture when legally/privacy feasible;
3. write the executable test first and confirm it fails for the intended reason;
4. implement the smallest change required to pass;
5. run the focused test;
6. run the relevant real-data/adversarial suite;
7. before a code-bearing commit, run the full application regression gate.

No implementation task is complete because code "looks correct". PASS requires observed executable evidence.

## 3. Real-data rule

Real-world data is the default validation substrate.

Accepted sources:
- public open-source repository samples intentionally published for demonstration/testing;
- public benchmark corpora with clear use terms;
- official/public API samples;
- user-authorized and appropriately redacted real screenshots/exports.

Synthetic data is allowed only to supplement real data for:
- deterministic fault injection;
- impossible/rare boundary construction;
- property/fuzz testing;
- controlled adversarial mutations;
- isolated parser contract tests when a real image is unnecessary.

Synthetic fixtures **do not satisfy the real-data corpus gate**.

Public leaks, exposed credentials, private dumps, or data whose publication appears unauthorized must not be used.

## 4. Ground-truth hierarchy

Ground truth must be attributable and must never be generated by the model under test.

Preference order:
1. source-published transcript/annotation paired with the real sample;
2. source-native structured export corresponding to the same evidence;
3. deterministic/manual annotation produced from the visible evidence and independently reviewed;
4. upstream project fixture only for structural contract tests.

An LLM or OCR provider output may be an observation under test, never the ground truth for itself.

## 5. Test-data readiness gates

### DATA-GATE-0 — Seed corpus
Minimum to design tests:
- >=1 real positive WeChat chat screenshot with attributable transcript/labels;
- >=1 real negative/non-chat WeChat UI sample or independently verified non-chat fixture;
- immutable source identifier (repository/path + blob/content hash or equivalent);
- provenance and license/usage review recorded.

### DATA-GATE-1 — Implementation start
Production WeChat vertical-slice implementation remains blocked until the corpus contains at least:
- **8 real screenshots**;
- **>=2 independent origins**;
- >=4 direct-message chat samples;
- >=2 samples containing visible timestamp separators or missing-timestamp conditions;
- >=2 partial/cropped/scroll-overlap conditions, either naturally occurring or deterministic mutations of real samples;
- >=2 negative/non-chat or unsupported-page samples;
- Chinese text represented; mixed Chinese/Latin/number/punctuation represented;
- ground truth for message order and speaker side on every positive sample;
- provenance/license/privacy metadata on every sample.

A single screenshot may satisfy multiple categories.

### DATA-GATE-2 — Release-quality corpus
Before claiming production-quality WeChat screenshot ingestion:
- >=25 real screenshots;
- >=3 independent origins, including user-authorized redacted data when available;
- coverage of at least two display scales/window sizes;
- direct chat plus at least one group/system/unsupported-content case;
- real or real-derived JPEG compression, resize, crop, blur, dark-theme/contrast, and overlap variants;
- provider-version benchmark results retained.

## 6. Stage separation

Tests are deliberately split so failures are diagnosable and replayable.

```text
Real Image Evidence
  -> OCR provider test
  -> immutable/versioned OCR-result fixture
  -> WeChat parser replay test
  -> wechat.normalized-chat@version
  -> canonical mapper test
  -> canonical history/replay/provenance test
```

A parser regression test should normally replay a stored OCR-result fixture rather than invoking live OCR. OCR provider quality is tested independently and again in end-to-end tests.

## 8. Exactness vs quality metrics

### Deterministic layers — exact requirements
The following acceptance criteria are **100% exact** for accepted fixtures:
- schema validity;
- message ordering after source-parser acceptance;
- speaker-side labels where ground truth is known;
- no fabricated timestamp;
- canonical mapping reproducibility;
- idempotency;
- provenance completeness;
- append-only history behavior;
- negative-page publication blocking.

### OCR/provider quality metrics
OCR is probabilistic and is benchmarked, not declared correct by assumption. Record at least:
- character error rate (CER) against labelled text where available;
- text-region/message recall;
- reading-order correctness;
- latency;
- provider/model/runtime version;
- failure/partial rate;
- effect of deterministic mutations.

Initial provider selection is evidence-driven. Do not hard-code a permanent numerical threshold until the real corpus is large enough to avoid overfitting one screenshot. The benchmark report must show raw per-sample metrics as well as aggregates.

## 9. Promotion rule for OCR-derived data

OCR output is extracted evidence, not automatically a canonical fact.

For the first vertical slice, a message may be promoted only through an explicitly documented deterministic acceptance path. If text/speaker/timestamp evidence is uncertain beyond the source contract, preserve the uncertainty or require corroboration/human review; do not silently coerce it into a fact.

## 10. Deterministic real-data mutations

Every adversarial sample derived from a real original records:

`original fixture ID -> mutation algorithm -> exact parameters -> tool/library version -> mutated hash -> expected invariant`

Initial mutation set:
- resize: 0.5x / 0.75x / 1.25x;
- JPEG re-encode: representative quality levels;
- left/right/top/bottom crop producing partial messages;
- mild Gaussian blur;
- contrast/brightness changes;
- deterministic dark-theme/contrast transform only when labelled as a synthetic visual mutation, never as a claim that WeChat generated the exact pixels;
- overlap pairs derived from one real screenshot or a real scroll sequence.

The mutation must be reproducible byte-for-byte from the same source + parameters where the selected image library permits deterministic output.

## 11. Test implementation order

Write tests in this order before production integration:

1. `WX-DATA-*` corpus/provenance validator;
2. `WX-SCHEMA-*` source-native schema tests;
3. `WX-PARSE-*` parser replay tests using immutable OCR-result fixtures;
4. `WX-MAP-*`, `WX-HIST-*`, `WX-PROV-*`, `WX-IDEMP-*` deterministic core tests;
5. `WX-OCR-*` shared-provider real-image benchmark;
6. `WX-E2E-*` real screenshot vertical slice;
7. `WX-ADV-*` real-data-derived mutation suite;
8. failure/replay/upgrade tests.

Production code is then written only to satisfy these already-defined contracts.

## 12. Completion definition

The WeChat test design is **TDD-ready** only when:
- this specification is versioned;
- `WECHAT_TEST_DATA_MANIFEST.md` identifies the current real-data corpus and gaps;
- DATA-GATE-1 is satisfied;
- expected outputs/labels are versioned;
- tests can be written without inventing unspecified behavior.

Until DATA-GATE-1 is satisfied, status is **TEST DESIGN READY / REAL CORPUS INCOMPLETE / PRODUCTION IMPLEMENTATION BLOCKED**.
